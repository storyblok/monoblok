# ADR-0029: CLI CRUD Command Conventions

**Status:** Accepted  
**Date:** 2026-11-19

## Context

`webhooks` is the first CLI command that manages a Management API resource one record at a time, and
other resources are planned. Their callers are scripts, CI jobs, and agents as much as people, so
the commands have to agree on verbs, flags, output, and errors. The shared layer in `src/lib/crud/`
is built now, with one resource, and has only been validated against webhooks.

## Decision

**Verbs and targets.** `list`, `get`, `create`, `update`, and `delete`, addressing a record by ID or
by its unique name. Several records sharing a name is an error listing their IDs, never a guess.

**Payload flags, strict; piped records, lenient.** `--set`, `--unset`, and `--data` are checked
against a field list generated from the API spec: an unknown or read-only field is a usage error. A
record piped in with `-` keeps only its writable fields and drops the rest without a warning, so the
output of `list` is valid input and a field the API adds later doesn't break a pipe. The cost: a
typo in a piped field name is lost silently.

**Stdin is buffered.** A command reads all of stdin before its first write, so a malformed record
fails the run before anything changes. This departs from the streaming consumer of
[ADR-0021](0021-cli-jsonl-pipe-contract.md), which story commands still need; a resource list is
small.

**Stale records are refused.** `update` sends only the fields that differ from the server. A piped
record carrying an `updated_at` that differs from the server's is refused unless `--ignore-stale`,
because the record's old values would undo changes made since it was read. The API has no
conditional write, so this is a client-side check with a small race.

**Errors follow stderr.** JSON lines on stderr when it isn't a terminal, the usual text on a
terminal, for every error of these commands, commander's own included. Other commands keep their
output.

## Alternatives Considered

- **Build the shared layer after the second resource.** Two resources show what is common. Building
  it first keeps webhooks from becoming a template that the next resource copies and adapts.
- **Hand-written or `satisfies`-typed field lists instead of codegen.** Less tooling, but each
  resource repeats what the spec says. The generated list is checked against the request types by a
  test that writes every field.
- **Zod schemas from the existing codegen option.** They validate too, but emit every Management API
  component and add `zod` to the CLI's runtime, and the API validates anyway.
- **Streaming stdin.** Bounded memory, but a malformed record could fail the run halfway through its
  writes.
- **`apply` (create or update) instead of `create --if-not-exists`.** It would converge a webhook's
  settings in CI, but needs its own rules for which fields win. `--if-not-exists` only creates, and
  keeps an existing webhook as it is. An upsert can come later as its own verb.
- **Writes that print the full record.** Result lines print `id`, `name`, and the action, so a
  write's output can't carry a secret and stays short. A caller that needs the record runs `get`.
- **JSON errors for every CLI command.** Right eventually, but it changes the output of commands
  people already parse.

## Consequences

- Webhooks fit the layer; access tokens don't yet. They have no get-one endpoint, their update
  returns no body, and the token value itself is the secret. The layer changes when they arrive.
- A resource whose `list` pages needs its adapter to page: targets by name, staleness checks, and
  `--if-not-exists` read one complete list per run.
- A CRUD command's memory grows with its input.
- `--set` and `--data` values from a config file are plain strings, so a secret set there reaches
  the log and report files unredacted. Accepted: a config file that holds a secret is already a file
  on disk with that secret in it.
