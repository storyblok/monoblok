# ADR-0033: Pagination Walks

**Status:** Accepted  
**Date:** 2026-10-12

## Context

Every paginated resource of `@storyblok/api-client` and `@storyblok/management-api-client` returns
one page per `list()` call. Reading a whole collection meant a hand-rolled loop over `page`,
`per_page`, and the `Total` header. `storyblok-js-client` offers `getAll()`, which fetches page 1
and then all remaining pages concurrently into one array.

A walk over the Content Delivery API reads offsets. Offsets only line up if every page comes from
the same published snapshot, and a publish mid-walk moves the CDN to a new `cv` (see ADR-0018). The
CDN serves an older `cv` only for URLs it still caches and redirects every other request to the
current one.

## Decision

**Paginated resources get two async generators next to `list()`: `pages()` and `iterate()`. Every
request goes through `list()`, so caching, throttling, and retries stay in one place.**

1. **`pages()` yields errors as values, `iterate()` throws.** `pages()` yields the `list()` envelope
   of each page, plus `page`, `perPage`, and `total`, and ends with a failed page's envelope, like
   `list()` resolves with `error`. With `throwOnError`, on the call or the client, it throws
   instead. `iterate()` yields items and has no envelope to carry an error, so it always throws.
2. **One failure type with a resume point.** A failed page becomes a `PaginationError` (a
   `ClientError`) with the failed `page`, a `reason`, the original `ClientError` as `cause`, and on
   the Content API client a `resumePage` and the `cv` to resume in. Transport failures are wrapped
   too, unlike in `list()`, so they keep the resume point. Aborting the caller's `signal` makes
   `iterate()` throw the abort reason unchanged.
3. **Content API walks detect a publish.** A published walk pins every later page to the `cv` the
   first page was served from. Since the CDN redirects a `cv` it no longer caches, a publish
   mid-walk usually fails the walk with `snapshot-changed` rather than reading the old snapshot to
   the end. A walk resumed past page 1 must be served from the `cv` it resumes in. Draft walks and
   `cache.cv: 'manual'` are not pinned.
4. **Serial, without lookahead.** Each page is fetched when the caller asks for it, so no request is
   in flight between pages, `break` needs no cleanup, and the caller's `signal` goes straight to
   `list()`. There is no concurrency option. A serial walk is predictable under rate limits and
   stops at the first failure.
5. **Bad pages fail.** A page without a list of items, or one that repeats the previous page, fails
   with `invalid-response` instead of ending silently or looping forever.
6. **The walk code is duplicated per client**, as ADR-0001 decided for shared code.

## Alternatives Considered

- **Standalone paginator functions** (`paginateStories(client, options)`, as in the AWS SDK v3).
  They tree-shake and cover new resources without wiring. But the clients expose resources as
  objects, and passing `stories.list` as a value loses the `const` generics that type resolved
  relations and links. The methods add about 1.4 KB gzip to `@storyblok/api-client` and 1.1 KB to
  `@storyblok/management-api-client` whether or not they are used.
- **A shared package for the walk.** Nearly all of the walk is identical between the clients, past
  the size at which ADR-0001 says to reconsider. A private package bundled at build time removes
  ADR-0001's objections (no release, no runtime dependency), but doesn't exist yet. Until it does,
  both clients run the same walk tests.
- **Prefetching the next page in `iterate()`.** It overlaps fetching with consuming, but a request
  is in flight at every `break`. Aborting it can abort a cached page's background revalidation,
  which runs on the same signal, and an early `break` still costs a request. Comparable SDKs
  (Stripe, Octokit, AWS SDK v3, Azure) don't prefetch either.
- **Restarting automatically after a snapshot change.** It would hide that items already yielded
  came from the old snapshot. The caller decides whether to restart, deduplicate, or give up.
- **`toArray()`.** `Array.fromAsync()` covers it on Node.js 22 and later.

## Consequences

- Callers that branch on error types see a `PaginationError` from walks where `list()` with
  `throwOnError` rejects a raw `TimeoutError` or `TypeError`. The original error is
  `error.cause.cause`.
- Walks over busy spaces fail more often than `getAll()`, which mixed snapshots silently.
- Changes to the walk must be made in both clients.
