# ADR-0029: CLI CRUD Command Conventions

**Status:** Accepted  
**Date:** 2026-11-19

## Context

`webhooks` is the first CLI command that manages a Management API resource one record at a time.
Other resources follow, and they build on `src/lib/crud/`. Scripts, CI jobs, and agents call these
commands as often as people do, so the commands have to agree on verbs, flags, output, and errors.

## Decision

**Verbs and targets.** `list`, `get`, `create`, `update`, and `delete` address a record by ID or by
its unique name. When several records share a name, the command fails and lists their IDs instead of
picking one.

**One layer, typed per resource.** A resource supplies a `CrudResource<T>` over its record type and
a field descriptor generated from the API spec. Request body types come from the descriptor; a
`json` field, which the descriptor can't type, takes its type from the generated request type and a
guard the resource supplies (`requestBodies`). A resource fails to compile when a field type differs
from the request type, when the request type has a field the descriptor lacks, or when a `json`
field has no guard. `createCrudCommand` adds a new top-level command, and `addCrudVerbs` attaches
some or all verbs to a parent, which can be an existing command such as `datasources`. When an
existing command moves to the layer, the layer's conventions win: a positional target instead of
`--id`, and `--yes` instead of `--force`.

**Payload flags, strict; piped records, lenient.** `--set`, `--unset`, and `--data` are checked
against the field descriptor: an unknown or read-only field is a usage error. A record piped in with
`-` keeps only its writable fields and drops the rest without a warning, so the output of `list` is
valid input, and a field the API adds later doesn't break a pipe. The cost: a typo in a piped field
name is lost silently.

**Stdin is buffered.** A command reads all of stdin before its first write, so a malformed record
fails the run before anything changes. It accepts JSONL, one object, or pretty-printed objects back
to back, so a file written by hand works too. Both depart from the streaming JSONL consumer of
[ADR-0021](0021-cli-jsonl-pipe-contract.md), which story commands still need. A resource list is
small.

**Writes are relative to the server record.** `update` composes the record as it should be (server,
then piped record, then `--data` as a JSON Merge Patch, then `--set`), and sends only the fields
that differ. A record that matches nothing fails, for `update` and `delete` alike, so a typo or the
wrong space doesn't pass. `delete --if-exists` skips it instead, so reruns pass, as
`create --if-not-exists` skips a name that exists.

**Stale records are refused.** A piped record whose `updated_at` differs from the server's is
refused unless `--ignore-stale`, because its old values would undo the changes made since it was
read. The API has no conditional write, so this is a client-side check with a small race.

**Dry runs check what the CLI can know.** A dry run applies each line to its in-memory copy of the
space, including a changed `updated_at`, so its own checks (required fields, names, stale records,
allowed values) treat each line as a real run would. It checks only values a write adds against the
allowed values, because the API keeps values that a record already has. Record-count limits, length
limits, and address formats are left to the real run. A dry-run error has no `status`: no request
answered it.

**Errors follow stderr.** When stderr isn't a terminal, every error of these commands, commander's
own included, is printed as one JSON line (`ErrorLine`). CI logs aren't terminals, so they get JSON
too. On a terminal, errors are the usual text. `details` is the API's error body as sent;
`allowed_values`, which the CLI adds, sits next to it, so it can't collide with a field the API
names. `ErrorLine` is the shape intended for the whole CLI. Until other commands move to it, it
lives in `src/lib/crud/` next to the pipe contract it belongs to, apart from `utils/error`.

**A batch stops when every further record would fail.** A rejected or under-scoped token (`401`,
`403`) and an unreachable API stop the run. While writing, the report counts the remaining records
as `unprocessed`; when reading the space fails, nothing is written and the run reports that one
error. Every other error fails only its record.

**Secrets stay out.** Secret fields are dropped from `list` and `get` output. A read-only
`has_<field>` flag, such as `has_secret`, tells whether the record has one; piped back in, it is
dropped like any field the API doesn't accept. Result lines carry only `id`, `name`, and the action,
and a dry-run diff shows a secret as `[changed]`. Only names of known fields are logged or repeated
in errors: an unknown name in a payload flag may be a misplaced secret, so log and report files get
`[redacted]` for it, and errors say "unknown field" without it. Secret values are logged redacted.
Errors are scrubbed of every secret value seen in the run that is at least 8 characters long, and
never repeat a target or the value of an unknown `--option=value`.

**Cancel is not failure.** Ctrl+C or Ctrl+D at the confirmation prompt exits 0 without writing, as
prompt cancellation does in every other command.

## Alternatives Considered

- **Build the shared layer after the second resource.** Two resources show what is common. Building
  it first keeps webhooks from becoming a template that the next resource copies and adapts.
- **Hand-written or `satisfies`-typed field lists instead of codegen.** Less tooling, but each
  resource repeats what the spec says.
- **Zod schemas from the existing codegen option.** They validate too, but emit every Management API
  component and add `zod` to the CLI's runtime, and the API validates anyway.
- **Streaming stdin.** Bounded memory, but a malformed record could fail the run halfway through its
  writes.
- **Rejecting unknown fields in piped records.** Would catch typos, but breaks `list | update -`
  whenever the API adds a field the installed CLI doesn't know.
- **Skipping a piped `update` that matches nothing.** That makes reruns pass, but a sync into the
  wrong space would do nothing and still exit 0.
- **`apply` (create or update) instead of `create --if-not-exists`.** It would converge a webhook's
  settings in CI, but needs its own rules for which fields win. `--if-not-exists` only creates. The
  docs show `create --if-not-exists` followed by `update` for convergence. An upsert can come later
  as its own verb.
- **Writes that print the full record.** Result lines print `id`, `name`, and the action, so a
  write's output can't carry a secret and stays short. A caller that needs the record runs `get`.
- **Text errors by default, JSON behind a flag or environment variable.** Every caller would have to
  know the flag before an error could be parsed. JSON on a non-terminal stderr needs nothing.
- **JSON errors for every CLI command now.** Right eventually, but it changes the output of commands
  people already parse.
- **A marker in the secret field itself.** `"[set]"` would be written back as the secret by
  `create -`, and `null` would clear every secret piped back to `update -`. A separate `has_secret`
  flag has neither problem.
- **`--include-secrets` on `list`.** Copies between spaces would keep their signatures, but secrets
  would land in shell history, pipes, and files. Setting a secret after a copy is one `update`.
- **Skipping a `delete` that matches nothing by default.** Reruns would pass without a flag, but a
  typo in a cleanup script would exit 0.
- **Stopping a batch on a plan limit.** Every create past the limit fails the same way, but the API
  marks that error only by its message text, which the CLI would have to match.
- **Removing repeated values from list fields.** The API stores `actions` with a value twice if it
  is sent twice. Removing repeats on the way out also changed lists that the server already stored
  with repeats, so an unchanged `list | update -` rewrote them. The CLI sends lists as given, as the
  API accepts them.
- **Redacting a short option with its value glued on.** Commander's error for an unknown `-xvalue`
  repeats `value`. Hiding it means rewriting commander's message text, and it only matters for a
  typo followed by a pasted secret. Unknown long options with `=value` are redacted.
- **Scrubbing short secret values from errors.** Replacing every occurrence of a one- or two-letter
  value garbles the message and gives the value away through the gaps. The API doesn't echo secrets
  in errors.
- **Exit 130 for Ctrl+C.** The shell convention, but every other command exits 0 on a canceled
  prompt.

## Consequences

- Access tokens don't fit the layer yet. They have no get-one endpoint, their update returns no
  body, and the token value itself is the secret. The layer changes when they arrive.
- A nested resource, such as datasource entries, needs a parent ID. `CrudScope` holds only `spaceId`
  today. The flag and the targeting rules for a parent are designed with the first nested resource.
- A resource whose `list` pages needs its adapter to page: targets by name, staleness checks, and
  `--if-not-exists` read one complete list per run.
- A CRUD command's memory grows with its input.
- `--set` and `--data` values from a config file are plain strings, so a secret set there reaches
  the log and report files unredacted. Accepted: a config file that holds a secret is already a file
  on disk with that secret in it.
- Redaction is per command (`RedactedOption`). A CLI-wide registry of sensitive options, checked
  where every parsed option is logged, would replace it.
