# ADR-0035: The Content API Client Re-Checks the Known `cv` Once per Window

**Status:** Accepted  
**Date:** 2026-11-26

Amends ADR-0018 for `@storyblok/api-client`.

## Context

With `cv: 'auto'`, `@storyblok/api-client` sends the known `cv` on every published request. The edge
serves a `cv` it still holds for up to a week and redirects only a request without a `cv`, or with
one it doesn't hold. Under ADR-0018, a publish becomes visible after the next poll of
`/cdn/spaces/me`, the next draft read, or `flushCache()`. An app that does none of these stays on
the last known snapshot for up to a week, while the docs present `cv: 'auto'` and `flush: 'auto'` as
automatic.

This affected stories already. Once the client learns the `cv` from `/cdn/links` redirects, it also
affects apps that only read links, such as sitemaps and navigation, which went out without a `cv`
before and were always current.

## Decision

**`@storyblok/api-client` keeps sending the known `cv` and checks it against the origin at most once
per 60-second window.**

1. **A check is a published read without a `cv`.** Once the window since the known `cv` was last
   learned or checked has elapsed, the next published read of stories or links that doesn't pin a
   `cv` goes out without one, even when the cache holds an entry. The origin redirects it to the
   current `cv`. The same `cv` keeps the cache. A newer one is adopted like any other response,
   which invalidates entries. Follow-up requests of a checked story, such as `rel_uuids`, send the
   `cv` its response reported. That narrows the window in which a publish mixes snapshots into one
   result but can't close it: the edge only serves an old `cv` for URLs it already cached, so a
   follow-up that lands after a publish is still redirected to the newer `cv`.
2. **The window restarts when the known `cv` changes or a check is claimed.** The known `cv` only
   moves to one the origin redirected to or a draft reported, since a stale edge read is rejected,
   so a changed `cv` is a current one. A check is claimed before it is sent, synchronously within
   the process, so concurrent reads send one check. A check uses up its window whatever it learns,
   so an outage or a response without a `cv` costs one attempt per window, not one per read. An
   error response, such as a 404 for a missing slug, was redirected like any other, so it teaches
   the `cv` in its URL, with or without `throwOnError`.
3. **Polls and unchanged draft reads don't restart it.** An unchanged `space.version` shows that
   nothing was published since the previous poll, not that the known `cv` is current. The check is
   the backstop for the cases where that inference fails, such as a lost invalidation. A draft
   reporting the known `cv` would cost a provider write per draft read to save one redirect per
   window.
4. **The window is shared through the provider.** The check time lives under its own reserved key,
   `sb:cv-checked:v1:<tokenId>`, read alongside the entry and the version watermarks and written
   when a check is claimed, before it is sent. A claim never rewrites the watermarks, so it can't
   undo a `flushCache()` or another process's response. The entry expires with the window, and a
   missing one reads as due. A time more than a window ahead reads as due too, so an instance whose
   clock runs far ahead can't suppress checks, while one a little behind the writer's clock doesn't
   check twice.
5. **Only stories and links check.** The API redirects them when they carry no `cv`. `/cdn/tags`
   teaches no `cv`, and `/cdn/datasources` and `/cdn/datasource_entries` answer a request without a
   `cv` from the edge cache like any other URL, so a check there could learn an old `cv`. Whether
   `/cdn/experiments`, which is redirected, reports the cache version or the space version is
   unverified: the two only differ under a Minimum Cache TTL. It doesn't check, so that question
   stays with ADR-0018.
6. **How a check reads depends on the strategy.** Under `cache-first` and `network-first` it reads
   network-first: it has to reach the origin, and a transient failure falls back to the cached
   entry. Under `swr` it runs as the background revalidation, so the read is answered from the cache
   and the next one shows the publish. A custom strategy handler decides itself, since it is the
   caller's statement of how reads use the network. Only a check whose read doesn't reach the
   network, because an `swr` revalidation of the same key is in flight or a custom handler answered
   from the cache, gives its claim back, so the next read sends it. Under `flush: 'manual'`, where
   only `flushCache()` changes what a cached key serves, a check with a cached entry answers from it
   whatever the strategy, checks in the background, and never writes the entry.
7. **Unaffected:** `cv: 'manual'`, which never sends a `cv`, caller-pinned `cv`s, drafts, and
   `/cdn/spaces/me`.
8. **The window is a constant, not an option.** 60 seconds matches the default cache TTL. The check
   costs at most one redirected read per window. Apps that need faster visibility poll or call
   `flushCache()` from a webhook; apps that need a fixed snapshot pin a `cv`.

`storyblok-js-client` is unchanged: it keeps the ADR-0018 guarantee, so a publish shows up there
only after a `/cdn/spaces/me` poll, a draft read, or `flushCache()`.

## Guarantees

For `@storyblok/api-client`, the ADR-0018 guarantee becomes: without concurrent requests and with
automatic invalidation, a publish is visible after the next poll of `/cdn/spaces/me`, the next draft
read, or the first published read of stories or links after the window since the last check elapsed.
Under `swr` it is one read later, or once a revalidation of that key in flight has settled. Under a
Minimum Cache TTL the redirect reports the same floored `cv` as a response body, so the check adopts
a new `cv` once the floor moves.

## Consequences

- This is a breaking change: a cached read is sent to the network once per window. That's at most
  one redirect and one CDN-cached read per window and shared provider, about 1,440 a day while
  traffic lasts.
- Under `cache-first` and `network-first`, the read that checks waits for the network.
- A failed check uses up its window, so a publish is noticed one window later. In the meantime the
  check's read is answered from the cache where an entry exists, once the client's retries are
  exhausted.
- Each published read of stories or links reads one more provider key, in parallel with the entry,
  and a check writes it once before it is sent. The claim isn't atomic across processes, so
  instances racing at window expiry can each send one check.
- With `flush: 'manual'`, a check moves the known `cv` without invalidating anything: requests that
  miss the cache fetch the new snapshot, while cached entries serve the old one until
  `flushCache()`, as after a draft read that reports a new `cv`.
- An app that reads neither stories nor links never checks.
- A custom `fetch` that rebuilds the `Response` loses its URL, and with it the `cv` a links response
  was redirected to. An app that only reads links then sends one check per window that learns
  nothing, and sees a publish no sooner than before this decision.
