<!-- Inserted after the first paragraph ("By default (`flush: 'auto'`)…"). -->

The CDN keeps serving the snapshot of a `cv` it holds after content is published. With `cv: 'auto'`,
the client therefore sends a published request for stories or links without the `cv` at most once a
minute, even if the cache holds a response for it. The API redirects that request to the current
`cv`, so the client picks up published changes without polling the spaces endpoint or calling
`client.flushCache()`. If that request fails, the client serves the cached response once its retries
are exhausted, so that read waits for the retries. With the `'swr'` strategy, the request runs as
the background revalidation, so the changes appear one request later. A custom strategy handler
decides whether that request uses the network. Clients that share a cache provider share this check.
With `flush: 'manual'`, requests that miss the cache return the new content, while cached responses
keep the old content until `client.flushCache()` runs.
