# Content migrations DSL: `defineMigration`

**Status:** Design, awaiting approval **Date:** 2026-09-21

## Problem

A content migration today is a plain JavaScript file that exports `(block) => block`. The target
component comes from the _filename_, so a change spanning two blocks means two files with no
atomicity between them. Nothing is type-checked: a misspelled component name produces a run that
matches zero blocks and exits 0, and a misspelled field silently writes a key nobody reads.

Rollback is worse. The runner snapshots each story's entire content to JSONL before migrating, and
`migrations rollback` PUTs that snapshot back with `force_update`. Any edit made between the
migration and the rollback is overwritten without warning, including edits to fields the migration
never touched.

`@storyblok/schema` now describes blocks and fields in TypeScript. Content migrations should be able
to read that description instead of guessing.

## Design

### Authoring

```ts
// .storyblok/migrations/295017/0007-rename-byline.ts
import { defineMigration } from "@storyblok/migrations";
import type { Schema } from "../../../schema";

export default defineMigration<Schema>((m) => m.field("article.author").renameTo("byline"));
```

`id` comes from the filename, so a rename moves the identity with the file and there is no second
place to keep in sync. `blocks` is inferred from the paths the ops touch, so nothing declares the
target twice.

**Three arities, because most migrations only have the current schema to hand.**

```ts
defineMigration((m) => …); // untyped: JavaScript projects, or before schema adoption
defineMigration<After>((m) => …); // typical
defineMigration<After, Before>((m) => …); // strict on both ends
```

`After` comes first because it is the one always available: it is the project's schema module, and
it types every name and value the migration writes. With one parameter, source paths resolve as
`FieldPathOf<After> | (string & {})`, so a surviving path autocompletes while a path the schema no
longer has still compiles. Naming `Before` as well tightens reads, turning a misspelled source path
back into an error. See Two schema versions.

**Two call shapes.** The callback is the forward-only case. The object exists so a hand-written
inverse has somewhere to live, which is also what makes `up` an honest name — it was only misleading
while no `down` could exist.

```ts
defineMigration<Schema>({ title, up, down });
```

`title` is a label for CLI output, nothing more; identity stays with the filename. `down` is a
fallback, not an override — see Rollback.

Several ops in one migration, applied in one pass over each story:

```ts
(m) => [
  m.field("article.author").renameTo("byline"),
  m.field("card.legacy_tags").remove(),
  m.field("article.price").asNumberField(),
];
```

The escape hatch, typed both ends:

```ts
(m) => m.block("meta").under("card").alter((block, ctx) => ({
  ...block,
  title: typeof block.title === "string" ? `${block.title} | Blog` : block.title,
  meta: [ctx.newBlock("seo", { og_title: block.title ?? "" })],
})),
```

Optional fields are `T | null | undefined`, so a free-form transform needs a guard before touching a
value. That's the most verbose part of the DSL and it's correct: the content genuinely can be null.

### Two schema versions

A migration straddles two schema versions, so one type parameter cannot describe it. Push the schema
first and the source field is already gone from the local schema, making `m.field("article.author")`
a type error; write the migration first and every field it creates is a type error. Both orderings
break, which the spike proved as a compile error before anything else was built.

The signature is `defineMigration<After, Before = After>`: a single signature with a default, not an
overload, so there is no resolution order to get wrong. `After` types rename and move targets;
`Before` types source paths, and `alter` is `(block: ContentOf<Before, N>) => ContentOf<After, N>`.

The order is target-first, which reads backwards against the migration's chronology and is worth the
trade: one type parameter has to mean the schema people actually have, and that is `After`. Under
one parameter, source paths widen to `FieldPathOf<After> | (string & {})`, so a field removed in
`After` is untyped rather than an error. That is precisely the case `Before` exists to tighten, and
it is now opt-in rather than the price of entry.

`Before` comes from a snapshot file generated next to the migration. It is generated by default;
`--no-before` skips it, for projects that never reach for the two-parameter form. It is an ordinary
schema module using `defineBlock` and `defineField`, scoped to the blocks the migration touches plus
blocks reachable through their `component_whitelist`, exporting
`export type Before = Schema<typeof schema>`. It is committed and frozen once shipped, which is what
lets a two-year-old migration still typecheck.

The snapshot is a typing artifact, not a schema archive. It drops server-assigned `id` and `pos` and
flattens the restriction keys. If we ever want it to double as an archive, that's a different
generator and the decision should be made deliberately rather than discovered.

The whitelist closure is transitive, so on a space where `page` whitelists a section that whitelists
everything it would drag in most of the schema. Bound it structurally instead of hoping: a block is
emitted in full only when the migration actually reads into it, and every other block reachable
through the closure is emitted as a name-only stub, enough to keep nested `bloks` fields typed. The
spike's toy schema produced 35 readable lines with two full blocks; the bound is what keeps that
true on a 60-block space. Worth measuring against a real customer schema, but no longer
load-bearing.

### Ops

`renameTo`, `moveTo`, `remove`, `asNumberField`, `asBooleanField`, an ordering op, and `alter`.

`renameTo` and `moveTo` are mechanically identical; the difference is validation, where `renameTo`
rejects an occupied target and `moveTo` allows it. The destructive case is easy to hit by accident,
so the distinction belongs in the API docs rather than in a reader's head.

Coercions are named for the wire form they write, not the JavaScript type they resemble. A Storyblok
`number` field stores a **string**, and an unset one stores `""`. The spike's first `asNumber()`
wrote a JSON number and looked fine until post-condition validation flagged it on every instance.

`.set(value)` is deliberately absent: without a predicate it means "overwrite this field on every
block in the space," which is never what anyone wants.

`section` and `tab` pseudo-fields are filtered out of the path union. They hold no content value, so
they aren't migratable.

### A field is a family

A translated field is a sibling key in the same block object: the default language keeps the bare
key, each translation adds `<field>__i18n__<lang>` with `-` replaced by `_` (`en-US` → `en_US`).

```json
{ "_uid": "article-root", "author": "Ada Lovelace", "author__i18n__de": "Ada auf Deutsch" }
```

Every op that names a field operates on the bare key **and** its suffixed siblings. A rename that
moves only the base key orphans the translation, and the orphan is unrecoverable rather than merely
stranded: the delivery API promotes a `__i18n__` key only while the base field is declared
`translatable`, and drops the rest. Rename the schema field, migrate the base key alone, and German
readers silently get the English string. This was measured on the wire, both directions.

Resolving the family from the block's own keys, rather than from the space's language list, also
catches translations for languages since removed from the space.

This holds for value ops as well as key ops. A field-level `alter` runs against the bare key and
every `__i18n__` sibling the block carries, so a transform written once is correct on a space with
three languages and on a space with none:

```ts
m.field("article.title").alter((v) => `${v} | Blog`);
m.field("article.title").alter((v, { language }) => (language === "de" ? `${v} | Blog` : v));
```

The second argument carries the language for transforms that genuinely differ by it. This is
contentful-migration's `transformEntryForLocale` without the ceremony: there, the tool iterates the
space's locales and hands you one at a time. Block-level `alter` is the exception — it hands you raw
keys, siblings included, and the family rule cannot help. That is the escape hatch and the docs
should say so.

Suffixed paths stay **out** of the typed path union, and the space's language list stays out of
`defineSchema`. Languages are space state (`space.languages`, with `space.default_lang_name`), not
schema, and one migration is expected to run against several spaces whose language sets differ.
Typing `article.title__i18n__de` would bind the migration to one space and be a lie on the next. It
would also make the union O(fields × languages) and invite exactly the half-family edits this rule
exists to prevent.

The path names the family; the runner resolves the members from the block's own keys at run time,
where the information is exact. `ctx.translations(block, field)` reaches them deliberately from
inside a block-level `alter`.

Validation rejects any op whose target already contains `__i18n__`, and post-condition validation
flags a block holding `X__i18n__*` with no `X` in `After`.

One thing the DSL cannot fix, so it belongs in the docs: the migration must run after the schema
rename, and the new field must keep `translatable: true`, or the delivery API discards the
translations no matter what the content says.

### Idempotency is enforced

Every migration must satisfy `f(f(x)) === f(x)`. The declarative ops already do: a rename whose
source is gone and whose target exists does nothing. Only `alter` can break the rule, and the runner
checks rather than trusts, applying each transform twice per block and comparing. One extra function
call per block costs nothing against the network, and it catches transforms that depend on
`Date.now()` or `Math.random()` for free.

```ts
// rejected: "alter on 'article' is not idempotent (block meta-a1)"
alter((b) => ({ ...b, title: `${b.title} | Blog` }));

// accepted
alter((b) => ({
  ...b,
  title: b.title?.endsWith(" | Blog") ? b.title : `${b.title} | Blog`,
}));
```

The rejected form is a latent bug either way; run it twice and you get `Post | Blog | Blog`. The
rule makes the migration correct, not merely compliant.

This is what demotes the ledger. A rerun is safe by construction, so a missing journal costs a
wasted pass over the space rather than corrupted content.

### Block addressing

Blocks are addressed by name at any depth: `m.block("meta")` reaches every `meta` instance wherever
it sits. The spike hit all four instances in one story, at depths 2 through 4, under two different
parents. The dot appears only in `block.field`, so there's no ambiguity between the two addressings.

`m.block("meta").under("card")` scopes to one location when the all-or-nothing default is wrong.

### Rollback

A migration produces patches; the runner applies them and records the inverse. The inverse needs no
algebra, because it's `diff(after, before)` computed while both trees are in hand. `alter` gets a
sound inverse for free, and no op has to be individually reversible.

This is why a hand-written `down` is not the primary mechanism. A schema `down` is symbolic — the
inverse of adding a column is dropping it, writable without reading a row — but the inverse of an
`alter` depends on the values it overwrote, so it can only be recorded, never declared. Every
forward-only tool in this space agrees: Sanity, contentful-migration, Prisma and Drizzle ship no
down for data, and Rails' auto-inverse is documented as off-limits for data migrations.

The cost is that patches are local, so rollback works only where the migration ran. That gap is what
the optional `down` closes, and **recorded patches take precedence over it**. Only the patches know
what the migration actually wrote, so only they can tell that an editor has since changed the field
and skip that block; a `down` is blind and would overwrite it. Preferring `down` would trade the
design's one real safety property for author convenience, silently, on the day of an incident.

So: patches when they exist, `down` when there are none, `rollback --force-down` when the author
knows the recorded inverse is wrong. `down` gets the same double-apply idempotency check as `up`,
since it is the half nobody tests. With neither available you roll forward with a new migration,
which is the same code reviewed and logged rather than dead code nobody has executed.

Patches address blocks by `_uid`, never by path, since array indices don't survive concurrent edits.
A block's patch excludes its descendant blocks, which are collapsed to a reference before diffing;
without that, a nested change is recorded twice and rollback double-applies it. Nested block lists
use uid-scoped insert and remove rather than whole-array replacement, so a block a human added to
the same array after the migration survives the rollback.

**The block is the unit of conflict.** A rename diffs to an unset of the old key plus a set of the
new one. Evaluating conflicts per op skipped the unset while letting the set land, producing a block
that held both field names at once: content no schema describes and no editor could write. That was
a real defect in the spike, caught on a live space, and it's the reason any conflicting op skips the
whole block patch.

**Absent is equivalent to empty.** When a story is opened in the Visual Editor, the editor fills
every `undefined` key the component schema declares with that field type's empty value: `""`,
`false`, `[]`, an empty richtext `doc`, an empty asset or multilink object. A plain open-and-save
with no user input is enough. So a key the migration's recorded `before` shows as absent can
legitimately read back as `""`, and a naive differ calls that a conflict.

Conflict detection therefore treats _key absent_ and _that field type's empty value_ as the same
state, resolved against `After`'s field types. Without the rule, rollback conflicts on every story
an editor has opened since the schema last gained a field, which is the worst possible population to
fail on. This is differ semantics; no ignore-list can express it, because the backfilled keys are
ordinary content keys that a migration may legitimately own.

**Blocks the patch never saw are reported, not ignored.** Duplicating a block in the editor assigns
a fresh `_uid` to the copy and to every nested child, without backfilling schema keys. A block
duplicated after a migration therefore carries the migrated shape under a uid no patch addresses,
and rollback would leave it silently untouched. Rollback reports these alongside conflicts and
missing uids: the existing "missing" class covers uids that vanished, not uids that appeared.

Rollback is therefore partial by design. It reports conflicts and skips those blocks. `--force`
overwrites them, prints what it will overwrite first, and is a deliberate CLI flag rather than a
library default anyone can pass.

Two consequences worth stating: a story that didn't exist at migration time has no inverse, and a
migration cannot express a rollback that is deliberately _not_ the inverse. Both are acceptable for
content; neither is true of schema.

### Block identity is a precondition

An `alter` that clones a block, or builds a block literal without a `_uid`, produces content the
backend re-uids on write. The patch and its inverse then address a uid that no longer exists, so the
migration appears to succeed and the rollback silently does nothing.

The runner refuses to write a story whose migration produced duplicate or missing uids, and fails
loudly. `ctx.newBlock(component, fields)` stamps a fresh UUID so the common case is hard to get
wrong.

### Validation

Path validation runs before anything is written: unknown block, unknown source field, rename onto an
occupied target, each reported with the known names.

Post-condition validation uses `validateStory` against **`After` only**. Against `Before` it is 100%
false positives by construction, reporting the migration's own intended changes as failures; a
rename produced unknown-field warnings and a coercion produced five hard errors. Against `After` it
earns its keep, and it's what caught the `asNumber` wire-format bug.

The post-condition validator mirrors the backend's own rules rather than approximating them, because
the backend now enforces them: a `number` is a string matching `/\A-?\d*\.?\d*\z/`, a `boolean` is
strictly `true` or `false`, a required field cannot be blank. Failing locally beats failing on story
300 of 4000.

Field constraints are not a per-space toggle anyone opts into. Recently created spaces enforce them
unconditionally; older spaces opt in per request. A violation is a 422 naming the field, the
component and the block uid, and it reaches blocks nested inside a richtext field. So
`asNumberField` writing the wire form is enforced rather than merely tidy: a JSON number would 422
every story on a current space.

Two ops can 422 mid-run by their nature: removing or renaming a _required_ field, and coercing to
`""`. The runner captures per-story errors and reports them at the end instead of dying partway. A
`--strict-mode` flag lets a legacy space dry-run against the rules it will inherit.

Translations are never validated by the backend, so a half-migrated family passes every check while
breaking the site. Nothing but the family rule catches it.

### Publish state

Migrations write drafts. A published story keeps serving its old shape until someone publishes it,
and then the migration goes live with no further action, possibly for an unrelated reason.
Publishing a parent folder pushes every descendant's migrated draft live at once.

That makes rollback asymmetric: rolling back the draft leaves production on the migrated shape. The
patch file therefore records each story's `published` and `unpublished_changes` state at migration
time, the existing `run --publish <all|published|published-with-changes>` flag carries over, and
rollback republishes exactly the stories the migration published. Today's runner already records
this state; the patch engine must not regress it.

Draft-only runs warn loudly and by count: _N stories are published; their live content still has the
old shape and will change the next time anyone publishes._

### Identity and ordering

`id` derives from the filename (`0007-rename-byline.ts`). `run` records each applied id and skips it
on a later run unless `--force`.

The ledger reports and locates; it does not guard correctness. Enforced idempotency does that, so a
rerun without a ledger wastes a pass over the space and changes nothing else.

One entry per line:

```jsonl
{
  "id": "0007-rename-byline",
  "space": "295017",
  "appliedAt": "2026-09-21T14:32:10Z",
  "checksum": "sha256:9f2a…",
  "reversible": true,
  "stories": 412,
  "blocks": 1183,
  "conflicts": 0,
  "patches": "rollbacks/0007-rename-byline.1758461530.jsonl"
}
```

`checksum` covers the migration source, so a migration edited after it ran is detectable instead of
silently diverging. `patches` locates the recorded inverses, and `reversible: false` marks a run
made without them so rollback fails loudly instead of doing nothing.

**The ledger is not committed to git.** It describes what was applied to _a space_, and a checkout
is not scoped to a space: the same branch pushes to development, staging and production. A committed
ledger would claim an id was applied everywhere as soon as it was applied anywhere, and two people
running against different spaces would collide in a file that was never shared state. Rails and
Prisma keep this in the database being migrated for the same reason.

What is committed is the code: migration files and their `.before` snapshots.

**Decided: the ledger and the patches stay local and gitignored.** Storyblok has no migrations
table, and inventing one (a datasource keyed by migration id, say) puts machinery in the customer's
space that an editor can delete by accident. The cost of staying local is that rollback works only
from the machine that ran the migration, and that CI reruns a migration it has no record of. Both
are acceptable because idempotency is enforced: a rerun is a wasted pass, not a corruption.

Story history was considered as a server-side home for the pre-migration tree, which would make
rollback work from anywhere. It was rejected for now because history retention is capped and the cap
varies by plan, so a busy space can age out the version a rollback needs. Rollback that works for
some stories and not others, depending on how much editing happened since, is worse than rollback
with a stated boundary.

```
.storyblok/migrations/295017/
  0007-rename-byline.ts            committed
  0007-rename-byline.before.ts     committed
  journal.jsonl                    gitignored
  rollbacks/0007-…-1758461530.jsonl  gitignored
```

One line per story in the patch file:

```jsonl
{
  "storyId": 222463449106949,
  "blocks": [
    {
      "uid": "meta-a1",
      "ops": [
        {
          "op": "set",
          "key": "author",
          "value": "Grace"
        },
        {
          "op": "unset",
          "key": "written_by"
        }
      ]
    }
  ]
}
```

## What the space verified

Against a real space, 70 checks with no failures:

- `_uid` survives MAPI updates at every depth, including inside a richtext field. The backend mints
  a uid only where a `component` node has none, and regenerates only the second and later duplicate
  within one story.
- No server defaults, no normalization, no key pruning. A no-op PUT reads back identical.
- `_editable` never reaches a migration reading through MAPI; it's injected by the delivery API and
  stripped on save.
- The headline claim holds: after a migration, an edit to an untouched field survives rollback, an
  edit to a sibling block survives, and an edit to the migrated field itself is reported as a
  conflict and skipped.
- Blocks embedded in a richtext field migrate and roll back end to end. Today's runner never reaches
  them, because its recursion only follows arrays whose elements carry both `_uid` and `component`.

Against the live Visual Editor, driven through the real UI:

- The ignore-list `_uid` / `component` / `_editable` is complete. The editor writes no key MAPI does
  not, no bookkeeping fields, no ordering markers, no uid churn at any depth. Those four names plus
  `blok` are reserved, so no user schema can collide with them.
- A one-field edit produces exactly one diff op. A plain open-and-save with no edit writes nothing.
- The editor backfills schema defaults into whichever block is loaded in the form, which is the
  finding behind the absent-equals-empty rule above.

A second run settled the rest. Field-level translation orphans on a naive rename, measured end to
end through the delivery API, which is what produced the family rule. The editor does not backfill
translated keys, so absent-equals-empty needs no i18n branch. Publish writes no key Save does not.
Drag-reorder changes array order only; duplication assigns fresh uids without backfilling. Field
constraints reject a JSON number in a `number` field with a 422 naming the block uid, and reach
inside richtext.

**Still unverified.** Release _deploy_ is source-grounded only, since it could not be triggered
through MAPI. Drag-and-drop was read from source rather than driven through the UI. The snapshot
closure has not been measured against a customer-sized schema, though the stub bound above makes
that a question of file size rather than correctness.

## Relationship to ADR-0009

ADR-0009 rejected a schema-level migration DSL partly because it "would require a new execution
engine." This design does introduce one: patch-based application with recorded inverses. The
justification is the rollback semantics, which the existing snapshot-restore engine cannot provide
at all.

It keeps 0009's central instinct. `schema push` remains where migrations are born; it already diffs
remote against local per field and classifies rename, removed and type-changed. It should now emit a
`defineMigration` call plus its `.before` snapshot instead of raw `block.new = block.old` strings.

An ADR follows once this design is approved.

## Compatibility

Existing `.js` migrations keep running unchanged: filename-derived targeting, the same
`migrations run` and `migrations rollback` commands, snapshot-based rollback. They gain nothing and
lose nothing, and one space can hold both kinds in one directory.

Discovery already discriminates on extension. `readMigrationFiles` skips anything not ending in
`.js`, so DSL migrations are invisible to every CLI version shipped so far and the legacy side needs
no compat shim at all. The new loader takes `.ts` and ignores `*.before.ts`, which is a schema
snapshot rather than a migration and must never be executed.

**`run`.** An argument naming a `.js` file behaves exactly as today. The positional means a
component there and an ordered id here, so rather than overload it, DSL migrations are addressed as
a set: bare `run` applies the pending ones in id order, `--id` picks one. `--filter` works on both.
Legacy migrations run first in a mixed directory, because one that replaces a block wholesale cannot
be diffed into patches and so cannot be ordered against the DSL ones.

**`rollback`.** Both formats live in `rollbacks/` and the line shape tells them apart, so there is
no naming convention to defend: legacy lines are `{storyId, name, content, published}` whole-story
snapshots, DSL lines are `{storyId, blocks:[{uid, ops}]}`. A legacy file keeps restoring by
`force_update` with the clobbering intact, which is what rolling back a legacy migration is supposed
to do. The filenames do not collide either — `<component>~<component>.<ts>.jsonl` against
`<id>.<ts>.jsonl`.

**`generate`.** Emits the DSL file, and its `.before.ts` unless `--no-before`, when the project has
a schema module; today's blank `(block) => block` when it does not, with `--js` to force it.
Authoring a new file breaks nothing, so the default can move.

**The ledger** covers DSL migrations only. Legacy ones stay outside it and re-runnable by hand, as
now; backfilling them would claim an applied state nobody recorded.

## Scope

Content only. `schema push` stays the declarative path for structure; a migration explains how
existing content moves to it. Folding both into one file would give the component schema two sources
of truth, and `renameTo` would then mean something different on each side.

**Releases are out of scope, and the runner refuses to run while any are pending.** A story written
into a release is stored separately and the story endpoints never show it. That content does not go
through the same normalization a story update does, so it can legitimately hold duplicate `_uid`s
the patch engine assumes cannot exist. Deploying the release replaces the story's draft wholesale,
discarding any migration applied after the release branched, silently. `--allow-pending-releases`
exists for someone who knows what they are doing and lists what will be missed; there is
deliberately no `--release` flag, because none of the engine's guarantees hold there.

Story-level translated stories are in scope: one draft carries every language through `__i18n__`
keys, and block uids are identical across languages, so migrating the draft is correct. Each
language's published copy still diverges independently until republished.

Import and story duplication are compatible. Both match nodes by `_uid`; duplication copies block
uids verbatim and regenerates only the story uuid, which is why a patch line is keyed by story id
and uid together and the engine never indexes by uid alone.
