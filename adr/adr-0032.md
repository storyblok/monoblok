# ADR-0032: React SDK Live Preview and Server Components Entry

**Status:** Accepted  
**Date:** 2026-11-26

## Context

`@storyblok/react` 8.x adopts the block registry model of ADR-0031 and drops data fetching:
applications fetch with `@storyblok/api-client` and pass the story in. Two questions are specific to
React:

- Live editing has to work in client-rendered apps and in React Server Components (RSC). In RSC,
  blocks render on the server, so a change in the Visual Editor has to render on the server again.
- Version 7 had a separate `/rsc` entry with its own `storyblokInit`, `StoryblokStory`, and
  `StoryblokLiveEditing`, and choosing the wrong entry failed with errors that didn't mention
  Storyblok.

## Decision

### 1. One `StoryblokPreview`, two implementations

`StoryblokPreview` takes `story` and `renderContent` in both implementations:

- **Client** (`@storyblok/react`): `renderContent` is a render function. The component keeps the
  live story in state (`useStoryblokState`) and calls `renderContent` on every change.
- **Server Component** (`@storyblok/react/rsc`): `renderContent` is a Server Action. The component
  awaits it once for the initial render, then a client runtime calls it again on every change,
  debounced, one call at a time, inside a transition so the current content stays on screen. A
  failed call keeps the last content that rendered.

`useStoryblokState` and `useStoryblokEditorEvent` stay public for custom setups.

### 2. The root import resolves by environment

The root entry has a `react-server` export condition that resolves to a build exporting everything
from the root, with the Server Component `StoryblokPreview` in place of the client one. The
`StoryblokPreview` a Server Component gets from `@storyblok/react` is the one that works there, and
editor auto-imports of the root are correct in both environments. `@storyblok/react/rsc` stays as an
explicit entry. TypeScript resolves the root types without the condition, so the client
`renderContent` type also accepts a function that returns a promise.

### 3. `renderContent` is the only server boundary

The Server Action receives only the story, which the browser sends, so it's untrusted input. The SDK
doesn't gate the action: draft mode is a Next.js concept, and the action also renders the initial
content for every visitor. The docs show how to render `StoryblokPreview` only in draft mode and
reject other calls in the action. Extra props reach the action through `.bind`, which the docs also
mark as untrusted.

### 4. Bounded warnings

The registry prints each warning once, and at most 100 distinct warnings. Block types come from the
story, and the Server Action renders any story it receives, so warnings without a cap would grow
server memory and logs with every made-up block type.

## Alternatives Considered

- **Keep `/rsc` as the only way to the Server Component** — Editor auto-imports choose the root
  entry, and the wrong `StoryblokPreview` fails with errors from Next.js. Rejected for the
  `react-server` condition, which can only be added before 8.0 without a breaking change.
- **Render the initial content from `children` and call the action only for updates** — Would let
  the action gate itself, but needs a second way to pass the initial content. Rejected for now in
  favor of documenting draft mode in the page.
- **Gate the action on draft mode in the SDK** — Ties the SDK to one framework. Rejected.

## Consequences

- Server Components can import everything from `@storyblok/react`.
- A setup without the `react-server` condition gets the client `StoryblokPreview` from the root;
  only RSC bundlers set it.
- Live editing stops after a client-side navigation inside the preview, because the Visual Editor's
  URL parameters are gone. The docs state it; a fix belongs in `@storyblok/live-preview`.
