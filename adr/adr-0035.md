# ADR-0035: The Content API Client Re-Checks the Known `cv` Once per Window

**Status:** Accepted  
**Date:** 2026-11-26

Amends ADR-0018 for `@storyblok/api-client`.

## Context

With `cv: 'auto'`, `@storyblok/api-client` sends the known `cv` on every published request. The edge
serves a `cv` it still holds for up to a week and redirects only a request without a `cv`, or with
one it doesn't hold. Under ADR-0018, a publish becomes visible after the next poll of
`/cdn/spaces/me`, the next draft read, or `flushCache()`. An app that does none of these stays on
the last known snapshot for up to a week, while the docs present `cv: 'auto'` and `flush: 'auto'` as
automatic.

This affected stories already. Once the client learns the `cv` from `/cdn/links` redirects, it also
affects apps that only read links, such as sitemaps and navigation, which went out without a `cv`
before and were always current.

## Decision

**`@storyblok/api-client` keeps sending the known `cv` and, under `flush: 'auto'`, checks it against
the origin at most once per 60-second window.**

1. **A check is a published read without a `cv`.** Once the window since the known `cv` was last
   learned or checked has elapsed, the next published read of stories or links that doesn't pin a
   `cv` goes out without one, even when the cache holds an entry. The origin redirects it to the
   current `cv`. The same `cv` keeps the cache. A newer one is learned like any other redirect,
   which invalidates entries. Under `cv: 'auto'`, follow-up requests of a story read that went out
   without a `cv`, a check or a cold read, such as `rel_uuids`, send the `cv` its response reported;
   under `cv: 'manual'` they send none, like every other request. That narrows the window in which a
   publish mixes snapshots into one result but can't close it: the edge only serves an old `cv` for
   URLs it already cached, so a follow-up that lands after a publish is still redirected to the
   newer `cv`.
2. **The window restarts when the known `cv` changes or a check is answered.** The known `cv` only
   moves to one the origin redirected to or a draft reported (ADR-0018), so a changed `cv` is a
   current one. A check uses up its window whatever it learns, so an outage or a response without a
   `cv` costs one attempt per window, not one per read. An error response, such as a 404 for a
   missing slug, was redirected like any other, so it teaches the `cv` in its URL, with or without
   `throwOnError`.
3. **Polls and unchanged draft reads don't restart it.** An unchanged `space.version` shows that
   nothing was published since the previous poll, not that the known `cv` is current. The check is
   the backstop for the cases where that inference fails, such as a lost invalidation. A draft
   reporting the known `cv` would cost a provider write per draft read to save one redirect per
   window.
4. **The window is kept in the process and shared through the provider.** Each process keeps the
   last check time per provider object, which answers most reads and lets concurrent reads in the
   process claim one check, synchronously. Only when that time says a check is due is the shared
   time read, from its own reserved key, `sb:cv-checked:v1:<tokenId>`, and a later one found there
   is kept locally. The claimant writes the shared time once the check is answered, never before the
   request, and a failing write costs the sharing, not the read. A claim never rewrites the
   watermarks, so it can't undo a `flushCache()` or another process's response. The shared entry
   expires with the window, and a missing one reads as due. Times are wall-clock milliseconds from
   `performance.timeOrigin + performance.now()`, comparable across processes; `Date.now()` before a
   request fails Next.js Cache Components prerendering. A time more than a window ahead reads as
   due, so an instance whose clock runs far ahead can't suppress checks, while one a little behind
   the writer's clock doesn't check twice.
5. **Only stories and links check.** The API redirects them in every space that redirects at all.
   `/cdn/tags` is never redirected, and `/cdn/datasource_entries` not in every space, so a check
   there can't be relied on to teach anything. Whether `/cdn/experiments`, which is redirected,
   reports the cache version or the space version is unverified: the two only differ under a Minimum
   Cache TTL. It doesn't check, so that question stays with ADR-0018.
6. **How a check reads depends on the strategy.** Under `cache-first` and `network-first` it reads
   network-first: it has to reach the origin, and a transient failure (a network error, a 5xx, 408,
   413 or 429) falls back to the cached entry once retries are exhausted; any other error is
   returned. Under `swr` it runs as the background revalidation, so the read is answered from the
   cache and the next one shows the publish. A custom strategy handler decides itself, since it is
   the caller's statement of how reads use the network; the strategy context doesn't say which read
   is the check. So a handler that answers from `cachedResult` whenever it has one never checks and
   shows a publish only once the entry's TTL expires. A check whose read doesn't reach the network,
   because an `swr` revalidation of the same key is in flight or a custom handler answered from the
   cache, gives its claim back, so the next read sends it. A check answered from a snapshot older
   than the highest `cv` seen, as an edge node can in a space whose API doesn't redirect, returns
   the cached entry where one exists. A check whose response teaches no `cv`, such as a links
   response whose URL was lost, isn't stored: it was sent without a `cv`, so nothing describes it.
7. **Unaffected:** `cv: 'manual'`, which never sends a `cv`, caller-pinned `cv`s, drafts,
   `/cdn/spaces/me`, and `flush: 'manual'`.
8. **The window is a constant; `flush: 'manual'` is the opt-out.** 60 seconds matches the default
   cache TTL. Under `flush: 'manual'` only `flushCache()` changes what a cached key serves, so a
   check there would cost a request a minute and change nothing; it is turned off. Apps that need
   faster visibility poll, or set `flush: 'manual'` and call `flushCache()` from a webhook. Pinning
   a `cv` is no opt-out: the origin redirects any pinned `cv` that isn't current, so a pinned read
   stays old only while the edge still holds that exact URL.

`storyblok-js-client` is unchanged: it keeps the ADR-0018 guarantee, so a publish shows up there
only after a `/cdn/spaces/me` poll, a draft read, or `flushCache()`.

## Guarantees

For `@storyblok/api-client`, the ADR-0018 guarantee becomes: without concurrent requests and with
automatic invalidation, a publish is visible after the next poll of `/cdn/spaces/me`, the next draft
read, or the first published read of stories or links after the window since the last check elapsed.
Under `swr` it is one read later, or once a revalidation of that key in flight has settled. Under a
Minimum Cache TTL the redirect reports the same floored `cv` as a response body, so the check learns
a new `cv` once the floor moves.

## Alternatives Considered

- **Poll `/cdn/spaces/me` from the client.** It is the cheapest signal, cached at the edge for two
  seconds, but an unchanged `space.version` only shows that nothing was published since the last
  poll. It can't catch a lost invalidation, such as a response racing the poll or an evicted
  watermark record, and under a Minimum Cache TTL it isn't comparable to the `cv` (ADR-0018). A
  timer would also keep serverless instances busy between requests. Apps can still poll; the check
  is the backstop.
- **Always check in the background.** Answering every read from the cache and checking behind it
  would keep reads fast, but the read that checks would return the old snapshot under every
  strategy, not only `swr`, and a serverless platform can freeze a background request with the
  invocation that started it, so the publish is noticed late. `swr` users already get this behavior.

## Consequences

- This is a breaking change: a cached read is sent to the network once per window. That's one
  redirect and one CDN-cached read per window and cache, about 1,440 a day while traffic lasts.
  Processes with their own in-memory cache, such as serverless instances, each pay it. Clients
  sharing a provider object share one check. Clients with separate provider objects over one store
  share the window once a check was answered; reads racing at window expiry in different processes
  can each send one.
- Under `cache-first` and `network-first`, the read that checks waits for the network.
- A failed check uses up its window, so a publish is noticed one window later. In the meantime a
  transient failure is answered from the cache where an entry exists, once the client's retries are
  exhausted.
- A provider read and write per check, and none in between: a read between checks reads the entry
  and the version watermarks only.
- Jobs that run longer than a window, such as static builds or paginated loops, can switch snapshots
  partway when content is published meanwhile. `flush: 'manual'` keeps one snapshot. `iterate()` and
  `pages()` pin a walk's later pages to the first page's `cv` and report a switch as
  `snapshot-changed` (ADR-0033), so a check never mixes snapshots within one walk.
- An app that reads neither stories nor links never checks.
- A `Response` rebuilt on its way to the client, by a custom `fetch`, an interceptor, or a framework
  cache such as Next.js `cacheComponents` prerendering, loses its URL. Stories still learn their
  body `cv` (ADR-0018). An app that reads only links then never learns a `cv`, so it never checks
  and caches with the TTL alone, as before links taught a `cv`.
- In a space whose API doesn't redirect, a check can't teach a `cv`.
